FOTA command response flow. 
 
• Platform shall receive the fota command response from device in the topic – 
  /dongle/<vinnumber>/ MQTTPROTOBUF /fotaCommandResponse. 
• Mqtt routing of the topic to the respective service. 
• The received payload is decoded. 
• DownloadfirmwareState is fetched, it shall be the states available in the proto 
• Verifies the correlation_id in the fotaCommandResponse payload.  
• If an active FOTA command is available with the received correlation_id as 
command_id, the command response is updated in database and is audited.

• The fota command for the VIN remains in progress, until a failure response is received 
or if the command is timed out from the platform. 
 
Device Join after FOTA installation. 
• Platform shall receive the device join payload from device in the topic for those VIN 
that are rebooted after FOTA installation  
  /dongle/<vinnumber>/ MQTTPROTOBUF / deviceJoined. 
• The received payload shall have FOTAID, which is the command_id of the FOTA and 
status, which is the status of installation. 
• On receiving a valid FOTAID and status as success. Then the active command is deleted 
from the DB considering the installation successful and audits the command transitions. 
 
FOTA command timeout 
• FOTA commands remain in InProgress state for a period of 7 days from the date and 
time at which the download trigger API is triggered to generate the command. 
• All FOTA commands that are aged over 7 days are timed out from platform and reset 
the FOTA states of the respective VIN so that a new fota downloadfirmware command 
can be triggered. 
• All command transactions are audited. 
 
FOTA command reset 
• FOTA commands remain in InProgress state for a period of 7 days from the date and 
time at which the download trigger API is triggered to generate the command. 
• This API can be used to reset the FOTA states of the respective VIN so that a new fota 
downloadfirmware command can be triggered. 
     jeep/ota/resetfotastate?vinNo=${VIN}&commandName=firmwaredownloadcommand 
• All command transactions are audited. 
FOTA command retry logic 
• If platform receives the device join payload from device for those VIN that are having 
an active fota command (command in progress ). The platform checks the FOTA and 
status in the received payload. 
• If there is no FOTAID and status for a VIN that is having the FOTA command as active, 
platform deletes the current active fota command and triggers a new fota command to 
the device in the same fota command Mqtt topic  
         - dongle/<vinnumber>/ MQTTPROTOBUF /fotaCommand

Buffered Telemetry 
• Vehicle Telemetry 
o Supports vehicle telemetry payloads send with protocol version 2.0.0 
o Receives the vehicle telemetry payload from the device over the MQTT topic  - 
/dongle/{vinnum}/MQTTPROTOBUF/vehicleTelemetry/history 
o Supports all CAN signals supported by vehicleTelemetry. 
o Decodes the protobuf encoded CAN data. 
o Retrieves the physical value of the signals, stores it for Audit  
o  The received value can be retrieved using audit APIs 
• Vehicle Events 
o Supports vehicle events payloads sent with protocol version 2.0.0. 
o Receives the vehicle telemetry payload from the device over the MQTT topic - 
/dongle/{vinnum}/MQTTPROTOBUF/events/history 
o Supports all the events. 
o Decodes the protobuf encoded payload and stores it for Audit 
o The received event can be retrieved using audit API 
• Location telemetry 
o Supports vehicle location payloads sent with protocol version 2.0.0. 
o Receives the location telemetry payload from the device over the MQTT topic -
/dongle/{vinnum}/MQTTPROTOBUF/locationTelemetry/history 
o Receives the gpsLat, gpsLong, gpsCourseAngle, gpsSignalQuality, 
gpsFixedStatus,  speed 
o Decodes the protobuf encoded payload and stores it for Audit. 
o The received event can be retrieved using audit API. 
• Alerts 
o Supports alerts payloads sent with protocol version 2.0.0. 
o Receives the alerts payload from the device over the MQTT topic - 
/dongle/{vinnum}/MQTTPROTOBUF/alerts/history. 
o Support all the alerts. 
o Decodes the protobuf encoded payload and stores it for Audit   
o The received alerts can be retrieved using audit API.
