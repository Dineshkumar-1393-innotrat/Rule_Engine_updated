1. INTRODUCTION  
1.1 Purpose 
The purpose of this document is to define the firmware functional behaviour of the Neoway-
based OBD Dongle used in the vehicle telematics ecosystem. This specification describes 
how the firmware interacts with the vehicle CAN/OBD-II interface, internal subsystems, 
LED indicators, and the CVIP cloud platform through southbound communication protocols. 
It establishes the required firmware behaviour for device lifecycle management, VIN 
decoding, telemetry publishing, event and alert handling, trip computation, and cloud 
communication, ensuring a consistent and verifiable implementation across firmware 
releases. 
1.2 Scope 
This specification defines the behaviour of the firmware running inside the Neoway OBD 
telematics device. 
The scope includes: 
• Device lifecycle handling 
• CAN/OBD-II signal processing 
• LED indication logic 
• Telemetry transmission rules 
• Event and alert detection 
• Trip computation logic 
• Southbound API interactions with the CVIP cloud platform 
Out of scope for this document: 
• Hardware schematics and electrical design 
• Mobile application logic 
• Cloud backend implementation 
• Detailed FOTA protocol specifications (only minimal behavioural references may be 
included)

2. SYSTEM OVERVIEW 
2.1 Product Summary 
The Neoway OBD Dongle is a vehicle-mounted telematics device that interfaces with the 
vehicle’s CAN/OBD-II network and communicates vehicle parameters to the CVIP cloud 
backend. 
The firmware is responsible for acquiring CAN signals, decoding essential vehicle 
information, computing trip and event states, and transmitting telemetry at defined 
intervals based on ignition status. 
It also manages internal lifecycle states to ensure secure onboarding, provisioning, and 
customer activation. 
2.2 Firmware Responsibilities 
The firmware implements the following high-level responsibilities: 
• Device Lifecycle Control 
• Manage transitions through Pre-Sales, Factory, Provisioned, Authorized, and 
Customer states. 
• Interact with cloud APIs for certificate download, state transitions, and 
provisioning. 
• CAN/OBD-II Signal Processing 
• Decode VIN from CAN ID 0x3E0. 
• Detect engine state from CmdIgnSts (0x46C). 
• Monitor MIL status via ENGINE_MIL_STAT (0x763). 
• Telemetry Publishing 
• Publish periodic telemetry every 60 seconds while engine is ON. 
• Publish two additional indicator telemetry samples when the engine 
transitions to OFF. 
• Event & Alert Handling 
• Detect ignition transitions and connection-status events. 
• Generate MIL alerts and device-specific driving alerts (towing, harsh events, 
etc., where applicable). 
1. Trip Computation 
• Compute TRIP_IDLE, TRIP_PENDING, and TRIP_ACTIVE states. 
• Apply user-configured thresholds such as MIN_TRIP_DISTANCE and 
MIN_IGN_OFF_TIME.

3. DEVICE LIFECYCLE MANAGEMENT  
3.1 Overview 
The OBD Dongle firmware operates within a structured lifecycle model that ensures device 
security, controlled activation, and predictable operational behaviour across different 
deployment phases. 
This lifecycle consists of five states: Factory, Provisioned, Authorized, and Customer, each 
representing a clearly defined stage in the device’s journey from manufacturing to full 
telematics operation. 
The lifecycle model guarantees that the device: 
• binds itself to the correct vehicle through VIN acquisition, 
• is authenticated and validated by the backend prior to operational use, and 
• enables customer-facing telemetry only after explicit activation. 
Each state imposes strict behavioural constraints on the firmware regarding what functions 
may or may not be performed, what identity must be used for communication, which 
subsystems must be active, and how transitions should occur. 
This section describes each lifecycle state in detail, along with operational characteristics, 
cloud interactions, and the expected transition logic. 
3.2 State Definitions 
3.2.1 Pre-Sales (Post Firmware Flash) 
Purpose 
The Pre-Sales state represents the initial firmware state immediately after production 
firmware flashing and end-of-line verification. 
In this phase, the device has not yet interacted with a vehicle or backend system in any 
meaningful way, and therefore performs only foundational security and network 
procedures necessary to prepare it for provisioning. 
This state ensures that the device enters the field with its cryptographic identity 
uninitialized, preventing premature data generation or unintended backend registration. 
Operational Characteristics 
• IMEI is the only identity used. The device has no association with a VIN or customer, 
and all cloud communication is expected to rely solely on IMEI. 
• Vehicle-facing interfaces remain inactive. CAN monitoring, OBD decoding, telemetry 
processing, event generation, and trip logic are fully disabled.

be activated to obtain the access token for CSR; GPS and CAN subsystems remain 
idle. 
• LED indicators may show only basic device readiness. No telematics-related LED

Mandatory Firmware Behaviour 
• Initiate CSR access-token request using IMEI as the identity.

3.2.2 Factory 
Purpose 
The Factory state is designed specifically for vehicle association. 
Here, the firmware must identify the vehicle by extracting a valid VIN from CAN traffic. 
This state ensures that each device is bound to a single, correct vehicle and prevents the 
possibility of misassociation. 
Operational Characteristics 
• IMEI continues to be the identity used. VIN is not yet accepted by the backend for 
device identification. 
• CAN subsystem actively listens for VIN on ID 0x3E0. The firmware reconstructs VIN 
using a sequence of VIN_MSG and VIN_DATA frames. 
• GNSS and GSM subsystems remain active. Network and positioning capabilities are 
ready but no operational data is sent.

Purpose

Operational Characteristics

device identifier. 
• Certificate-based authentication becomes active. The device now holds its 
operational certificate for secure cloud communication. 
• Telematics features remain disabled. Telemetry, alerts, events, and trip logic remain 
inactive until authorization. 
• Subsystems remain monitored but idle. CAN/GPS/GSM are active but do not trigger 
data transmission.

Operational Characteristics

• Identity remains VIN.

• Store lifecycle state as AUTHORIZED in persistent memory. 
• Listen for customer activation commands (cloud or SMS). 
• Keep all subsystems active and validated (GSM, GPS, CAN). 
• Suppress all telemetry and operational triggers.

3.2.5 Customer 
Purpose 
The Customer state is the final operational state in which all telematics functions are 
enabled. 
The device is now assigned to a specific end user, and all data capture, processing, and 
communication workflows are active. 
Operational Characteristics 
• Identity transitions to MSISDN. Cloud routing is now subscriber-based. 
• Telemetry fully active. The device publishes telemetry every 60 seconds during 
engine ON and generates D5/D6 samples after engine OFF. 
• Events and alerts are enabled. Ignition transitions, MIL status, towing, harsh driving, 
and connection status are fully monitored. 
• Trip FSM operates continuously. Idle  to Pending to Active transitions occur based 
on engine status and movement thresholds. 
Mandatory Firmware Behaviour 
• Enable all telematics modules including telemetry, events, alerts, and trip logic. 
• Maintain full monitoring of GPS, GSM, and CAN subsystems. 
• Persist Customer state across all resets. 
• Respond to backend command messages using MSISDN identity. 
Cloud Interaction

4.FIRMWARE FUNCTIONAL 
REQUIREMENTS 
 
 4.1 OBD-II / CAN Signal Handling  
The firmware shall continuously interface with the vehicle’s CAN bus to acquire, decode, 
and validate essential OBD-II signals required for VIN identification, ignition state tracking, 
MIL monitoring, telemetry generation, event detection, and trip state computation. 
The CAN subsystem is a critical source of truth for the dongle; therefore, decoding accuracy, 
timing responsiveness, and error resilience are mandatory requirements.The following 
subsections detail all CAN-related behaviours implemented by the firmware. 
4.1.1 VIN Decoding  
Purpose 
VIN decoding serves as the foundation of the device–vehicle binding process. 
It is the very first critical step through which the dongle establishes its identity relative to 
the vehicle in which it is installed. 
A correct VIN must be extracted before the device proceeds with cloud provisioning, 
ensuring that backend systems can uniquely associate the dongle to a specific vehicle and 
that all subsequent telematics data is attributed to the correct asset.. Therefore, the 
decoding logic must be robust enough to handle fragmented transmissions, intermittent 
CAN reception, and ordering challenges, while still ensuring a clean, validated, and complete 
17-character VIN before lifecycle progression is allowed. 
The device must not advance to provisioning or certificate download until the VIN is fully 
and correctly decoded, verified, and securely stored, as this value forms the permanent 
binding between the telematics hardware and the vehicle’s backend digital identity. 
Signal Processing Requirements  
1. Continuous Monitoring 
The firmware must listen for CAN ID 0x3E0 at all times whenever CAN 
communication is active. 
The listener may not be rate-limited or triggered; it must run continuously to avoid 
missing any VIN fragments. 
2. Fragmented Data Handling 
The VIN is transmitted across multiple CAN frames. 
o VIN_MSG indicates the positional index of the fragment. 
o VIN_DATA contains 7 bytes of the VIN. 
The firmware must reconstruct the VIN strictly in ascending VIN_MSG order, even if 
frames arrive out of sequence.

3. Assembly Rules 
o Concatenate VIN_DATA according to VIN_MSG index positions. 
o Discard any overlapping or duplicate VIN_MSG fragments unless confirmed 
identical. 
o Buffer must always track which segments are received and which are 
pending. 
4. Validation Rules 
The VIN must be validated against: 
o Allowed alphanumeric character set 
o Total length = 17 bytes 
o Absence of incomplete or missing fragments 
5. Persistence Requirements 
Once reconstructed, the VIN must be stored in secure, non-volatile memory so that 
reboots do not require reacquisition unless CAN inconsistencies are detected. 
 
4.1.2 Engine State Handling (Ignition Detection) 
Purpose 
Ignition state serves as one of the most critical inputs into the telematics firmware, acting as 
the primary trigger for controlling telemetry scheduling, managing the Trip Finite State 
Machine (FSM), determining alert evaluation windows, and coordinating multiple timing-
dependent behaviours within the device. 
Because ignition status directly reflects whether the engine is running or stopped, it 
influences not only real-time telemetry publication but also trip start/stop boundaries, MIL 
evaluation timing, and power management strategies. 
Incorrect ignition interpretation could result in premature trip starts, missed trip ends, 
incorrect telemetry patterns, or misaligned alert evaluation, all of which impact the 
correctness of backend analytics. 
The firmware must therefore handle ignition decoding with the same level of priority and 
precision as VIN and MIL processing. 
Signal Interpretation Requirements 
The firmware shall derive engine state exclusively from the CmdIgnSts signal received on 
CAN ID 0x46C from the BH2-CAN network. No alternative signals or fallback heuristics may 
be used to infer ignition. 
The mapping is: 
CmdIgnSts Interpretation Engine State 
0x4 RUN Engine ON 
0x5 START Engine ON 
Other values ACC / OFF / Unknown Engine OFF

Mandatory Firmware Behaviour  
1. Latency Requirements 
The firmware must update its internal ignition state within a single CAN cycle of receiving a 
new CmdIgnSts frame. 
This ensures instantaneous reaction to engine transitions, allowing the device to: 
• initiate telemetry scheduling without delay, 
• trigger Trip FSM transitions at the correct boundaries, 
• align MIL evaluation timing with actual engine runtime, and 
2. Event Triggering 
Ignition ON and OFF transitions must generate events only when a genuine state 
change occurs, meaning: 
• If CmdIgnSts repeats the same value consecutively, no additional events must be 
emitted. 
• Events must reflect true transitions, not repetitive CAN frames. 
Example: 
• 0x4 → 0x4 → 0x4 → 0x4 → No event 
• 0x4 → 0x0 → Ignition OFF event 
• 0x0 → 0x4 → Ignition ON event 
This prevents event spamming and ensures clean backend event logs. 
3. Input Quality Handling 
CmdIgnSts may momentarily oscillate due to: 
• CAN noise, 
• mechanical switch chatter inside the ignition system, 
• transitions during engine cranking, 
The firmware must therefore apply minimal debouncing, ensuring: 
• false transitions (OFF→ON→OFF→ON within milliseconds) do not cause 
premature events; 
• but responsiveness is not compromised. 
Debounce limit must not exceed 100–200 ms, ensuring: 
• timely reaction to real ignition changes, 
• suppression of jitter-induced false triggers.

This is important because overly aggressive filtering would cause late telemetry or trip 
transitions, whereas no filtering would produce unstable state behaviour. 
 
 
4. CAN Dropout Conditions 
If the firmware does not receive CmdIgnSts for a defined timeout period (recommended ~3 
seconds): 
• It must conservatively assume Engine OFF, 
• Because the absence of ignition information typically indicates either ignition truly 
OFF, CAN bus inactive, or power state transitioning. 
Firmware must then: 
• Immediately halt telemetry scheduling, 
• Move Trip FSM toward stop evaluation, 
• Pause MIL evaluation and post-engine-off behaviours, 
• And log the dropout internally for debugging. 
This rule protects the device from continuing operational behaviour during vehicle 
shutdown or CAN bus inactivity. 
 
4.1.3 MIL Status Monitoring (Engine Malfunction Indicator)  
Purpose 
MIL monitoring informs health alerts for engine malfunction or emission system 
errors. 
Because MIL is time-sensitive and critical for diagnostics, firmware must follow 
strict timing and evaluation rules. 
 
Mandatory Evaluation Logic  
1. Delayed Evaluation Requirement: Firmware must not evaluate MIL immediately 
upon Engine ON. It must wait for 5 continuous seconds after detecting Engine ON to 
avoid transient MIL readings. 
2. Alert Generation Rules:  
o MIL = 0x1 or 0x2 after 5s → MIL Alert ON 
o MIL = 0x0 after 5s → MIL Alert OFF 
Alerts must be generated only on state transitions, not continuously. 
3. Telemetry Inclusion; MIL status must be included in periodic telemetry frames 
whenever Engine = ON. 
4. Error Handling 
If CAN ID 0x763 is missing for multiple cycles: 
o The firmware must temporarily retain the last known MIL state.

o After a timeout, the MIL status must be marked unknown, and no new alerts 
must be generated until valid data is received. 
5. MIL Reset Behaviour 
If MIL transitions from ON to OFF: 
o Firmware must generate an Alert OFF notification. 
o Clearing of MIL must not reset trip states or telemetry schedules. 
 
4.1.4 Handling Missing, Invalid, or Corrupted CAN Data  
Purpose 
The Malfunction Indicator Lamp (MIL) is one of the most important diagnostic signals 
exposed through the vehicle’s CAN network. It reflects critical information related to 
emission system failures, engine operating anomalies, and regulatory compliance faults that 
must be communicated to backend systems and, in turn, to end users and maintenance 
personnel. 
Because MIL transitions often indicate actionable service requirements, the firmware must 
monitor this signal with exceptional accuracy, ensuring that alerts are neither delayed nor 
triggered prematurely. 
MIL monitoring is highly time-sensitive; it must consider engine warm-up behaviour, CAN 
stabilization periods after ignition, and system-wide transient conditions. 
Therefore, firmware must enforce strict timing, evaluation logic, and error-handling rules to 
ensure reliable and trustworthy MIL alerting behaviour. 
Processing Rules  
1. Missing Data 
If a required CAN signal is temporarily missing, the firmware must apply a controlled 
response strategy that prevents false transitions or abrupt behavioural changes: 
• Short Duration Absence (<3 seconds) 
When a CAN signal such as CmdIgnSts, VIN fragments, or MIL status is not received 
for a brief period, the firmware should continue using the last known valid value. 
This prevents unnecessary transitions, such as: 
o Engine ON to Engine OFF due to one missed frame 
o MIL ON/OFF oscillations 
o VIN validation aborts during transient gaps

4.3 Telemetry Publishing Logic 
The firmware is responsible for publishing vehicle telemetry data to the CVIP backend 
based on well-defined engine state transitions and timing rules. 
Telemetry publishing follows a strict schedule that is tied directly to the engine ON/OFF 
condition, ensuring that the backend receives periodic status updates during active vehicle 
operation and a final set of indicator packets when the engine shuts down. 
This section defines all firmware behaviours associated with telemetry timing, data 
sampling, and conditional publishing. 
4.3.1 Purpose 
Telemetry publishing provides real-time visibility into vehicle operation, enabling backend 
systems to compute driving behaviour, trip summaries, alerts, and diagnostics. 
Because continuous transmission is not required when the engine is off, and because OEM 
backend systems must receive one or two indicator samples immediately after shutdown, 
firmware must implement a precise and predictable telemetry schedule. 
The telemetry engine must: 
• publish only during engine ON, 
• follow a 60-second publish cycle, 
• send two additional samples just after engine OFF, 
• then remain silent until the next valid engine ON event. 
These rules prevent unnecessary network usage and ensure backend analytics remain 
accurate. 
4.3.2 Telemetry Trigger Conditions 
Telemetry is triggered exclusively by engine state, derived from CmdIgnSts: 
• Engine ON → Telemetry active 
• Engine OFF → Telemetry halted, except for shutdown indicator packets 
No other signal (speed, movement, trip status, CAN flow) can independently trigger 
telemetry publishing.

When the engine is ON, the firmware must: 
1. Publish telemetry every 60 seconds without deviation.

4.5 Alert Framework 
The Alert Framework defines all high-priority conditions under which the firmware must 
generate and transmit alerts to the CVIP backend. 
These alerts represent exceptional or safety-relevant situations, such as engine 
malfunction indications, abnormal vehicle movement, or aggressive driving patterns, and 
therefore require immediate and accurate reporting. 
Unlike periodic telemetry, which follows a fixed schedule, alerts are evaluated continuously 
based on signal changes and are triggered when specific logical conditions become true or 
false. 
The firmware must implement alert generation in such a way that: 
• each alert is raised only when a real transition into an abnormal condition occurs, 
• each alert is cleared only when the corresponding condition returns to normal, 
• no duplicate alerts are generated while a condition remains continuously active, and 
• alert evaluation is suspended when the underlying sensor or CAN information is 
unavailable. 
The subsections below define the alert types, their signal sources, evaluation logic, and 
reporting behaviour. 
4.5.1 MIL Alert (Malfunction Indicator Lamp) 
The MIL alert indicates that the vehicle’s engine or emission system has reported a 
diagnostic condition requiring attention. 
This alert is based on the MIL status reported by the engine control system over the CAN 
bus and is tightly coupled with engine state and regulatory expectations. 
Signal Source 
• CAN ID: 0x763

• Signal: ENGINE_MIL_STAT 
Evaluation Timing 
The firmware must not evaluate or act on MIL information immediately at engine start. 
After the engine transitions to ON, the firmware must wait for a continuous period of five 
seconds before evaluating the MIL status, allowing all ECUs to complete their internal 
initialization and avoiding false indications during startup. 
Alert Conditions 
• The firmware must generate a MIL Alert ON when: 
o the engine has been in the ON state for at least five seconds, and 
o ENGINE_MIL_STAT indicates a non-normal condition (for example, values 
corresponding to “On” or “Blinking” as defined in the CAN signal 
specification). 
• The firmware must generate a MIL Alert OFF when: 
o the engine has been in the ON state for at least five seconds, and 
o ENGINE_MIL_STAT returns to the value representing “Off”. 
Operational Behaviour 
Once a MIL Alert ON has been generated, the firmware must not repeatedly reissue the 
same alert as long as the MIL status remains continuously in the abnormal range. 
Similarly, once a MIL Alert OFF has been sent, no further MIL-clear alerts must be sent until 
the MIL again transitions from Off back to an abnormal condition. 
If CAN frames for ENGINE_MIL_STAT are not received for a defined timeout period, the 
firmware must treat the MIL status as unknown and must refrain from generating any new 
MIL ON or OFF alerts until valid data is again available.

4.6 Trip Management  
The Trip Management subsystem defines how the firmware interprets ignition states, 
vehicle motion, and distance accumulation to classify driving activity into well-defined trip 
phases. 
Trips are fundamental to backend analytics such as drive scoring, distance computation, 
fuel estimation, and behavioural insights. 
To ensure consistency in trip boundaries, the Trip Engine must use strict thresholds and 
timing windows as defined by OEM parameters and must avoid false trip starts or early trip 
terminations. 
The Trip Engine operates as a finite state machine (FSM) consisting of three primary states: 
• TRIP_IDLE 
• TRIP_PENDING 
• TRIP_ACTIVE

Represents the intermediate stage where the engine is ON and movement may be

• Engine ON is detected, or 
• Vehicle shows initial motion sufficient to indicate possible drive initiation. 
Operational State

• Firmware must accumulate distance incrementally. 
• Firmware must measure continuous engine ON duration. 
• No trip is reported to backend yet; trip metadata is internal only.

• All thresholds are evaluated continuously.

Represents a valid, ongoing trip.

• Minimum distance threshold is exceeded while in TRIP_PENDING. 
Operational State

intermittent signal loss.

1. Engine transitions to OFF, and 
2. Engine remains OFF longer than MIN_IGN_OFF_TIME, ensuring genuine trip

3. No significant movement is detected during the OFF window.

The Southbound Communication subsystem defines how the OBD firmware interacts with 
the CVIP backend across all lifecycle stages. 
This section specifies the API endpoints, identities (IMEI, VIN, MSISDN), payload 
responsibilities, and behavioural constraints that govern communication between the 
device and the cloud. 
Each lifecycle state defined in Section 3 mandates a specific cloud exchange pattern, and the 
firmware must follow these interactions exactly to maintain pairing integrity, provisioning 
correctness, and secure end-to-end telematics flow. A concise summary of all required API 
calls and their usage is provided in Table 5-1, followed by telemetry and alert transmission 
rules in Table 5-2 and Table 5-3. 
 
5.1 Overview of Southbound Lifecycle Communication 
During the device lifecycle, the firmware transitions through Pre-Sales, Factory, 
Provisioned, Authorized, and Customer states. 
Each transition requires a specific southbound action, either to request a certificate, join the 
platform, acknowledge commands, or publish operational data. 
The firmware must ensure that API calls occur only when the device is in the correct 
lifecycle state, using the identity dictated by that state. 
Retry behaviour, identity selection, and payload formation must all comply with the 
associated API requirements and security expectations. The complete set of required 
interactions is summarized in Table 5-1. 
 
5.2 Telemetry Publishing Rules (Southbound Layer) 
Once the device reaches Customer state (refer Section 3.2.5), telemetry becomes the 
primary data channel used to communicate operational vehicle information. 
Telemetry is published strictly based on engine ON/OFF transitions, and the firmware must 
observe the timing and suspension rules described in Section 4.3. 
The southbound layer must ensure reliable packet delivery, queueing if GSM connectivity is 
unavailable, and retry logic for cloud timeouts. Telemetry behaviour during ON and OFF 
windows is summarized in Table 5-2.

5.3 Event and Alert Transmission Requirements 
Events and alerts represent condition-driven notifications that must be transmitted to CVIP 
outside the regular telemetry schedule. 
Unlike periodic telemetry, events and alerts must be delivered immediately upon 
occurrence, provided GSM connectivity is available. 
If connectivity is temporarily unavailable, the firmware must queue these messages and 
transmit them at the earliest opportunity once the network is restored. 
The firmware must ensure that event and alert messages reflect state transitions only, in 
order to avoid duplicate reporting. A summary of event and alert upload mappings is shown 
in Table 5-3.
