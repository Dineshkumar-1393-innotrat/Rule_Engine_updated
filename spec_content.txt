7.2 MQTT 
MQTT shall be the protocol interface between the CVIP and Dongle. The scalable and enterprise 
grade MQTT broker (VerneMQ) used on the CVIP currently supports only MQTT v3.1.1.  
QoS level-1 shall be used for the MQTT publish/subscribe requests for all topics. Use of QoS level-
2 will not be evaluated as it involves overheads and needs to be prototypes and performance 
benchmarked.

7.2.4 MQTT Keep Alive  
The clients connecting to MQTT broker in CVIP are expected to configure the keep alive time of 
10 minutes. This means that the client is expected to publish at least one message within 10 
minutes from the last communicated message. If there is no communication of message for the 
past 10 mins, then the client is expected to publish a PingReq message. 
 
The MQTT broker shall wait for 15 minutes ( 1.5  times the keep alive timer) to abort a MQTT 
session if there is no communication from the client. 
 
7.2.5 MQTT LWT configuration 
Dongle is expected to configure the deviceJoined topic as LWT topic in the MQTT client 
configuration.  
Topic Name - /dongle/<VIN>/MQTTPROTOBUF/deviceJoined

configured as “DISCONNECTED”.

• Dongle is powered up and TLS Session (TLS 1.2) is established. 
• After that, DONGLE publishes message on the topic  
“/dongle/{VIN}/{protocol}{data format}/deviceJoined” to CVIP. 
• On receiving the device Joined message, CVIP does IMEI validation and publishes 
message on the topic  
 “/dongle/{VIN}/{protocol}}{data format}/deviceJoinedRsp” to the DONGLE 
acknowledging that device discovery has successfully completed. 
• CVIP shall send an Authorized state update command to the device to update the 
state of device. 
• Device discovery shall have exponential retry logic implemented

8.3.6 Device Joined – Corner Cases or Negative Scenarios Handling 
• If internet is not connected during power on or MQTT session establishment, then Dongle 
will not queue up the Device joined message as per retry logic and communicate a burst 
of Device joined Message to CVIP server. Instead, Dongle shall wait till the Internet 
connectivity is established and only then initiate a device joined message. 
• If Device joined failure DTC is set, then the Dongle shall not initiate a device joined retry. 
• FOTA status parameter in device join message shall be applicable only in the following 
scenarios. 
o FOTA status parameters such as FOTAID, status, version would in added only in 
case FOTA update/install has been started. 
o FOTA status parameters shall not be added in any device join message happened 
before FOTA Update/Install starting.

• After downloading the package, the Dongle shall verify the signature of the FOTA package

DecodeCCPUSignatureAuthenticationFailure 
• After signature verification, the Dongle shall verify the file size mentioned in the FOTA 
package matches with the actual encrypted FOTA package.  
o If the file size matches, then Dongle can proceed to next step 
o If the file size mismatches, then the Dongle shall send the error code 
DownloadInProgressCCPUFilesizeNomatched or 
DownloadInProgressVMPUFilesizeNomatched 
• If the file size matches, then Dongle shall use the encryption key to decrypt the FOTA 
package. 
o If the decryption is successful, then Dongle can proceed to next step. 
o If the decryption fails, then Dongle shall communicate 
DecodeVMCUWrongEncryptionFile or DecodeCCPUWrongEncryptionFile 
• If the decryption is successful, then Dongle shall verify the decrypted file size need to be 
verified with the rawSize parameter in FOTA download command.

13. Telemetry Streams 
As Telemetry streams are continuous and periodic, decoding the CAN frames in Dongle and 
setting the values in proto buffers would increase the size and overhead on the payload sent 
from Dongle to Cloud.  
Hence  Vehicle Telemetry streams shall be sent as CAN frames from Dongle and decoded in the 
CVIP cloud.  
 
Based on communication frequency and sampling frequency, these frames are accumulated 
and then sent to cloud.  
 
Types of telemetry streams in CVIP  
• Vehicle Telemetry – CAN messages are sent in Protobuf directly

15. Edge Computing 
Edge Computing 
Edge computing focuses on processing closer to the source of data. However, Dongle is not as 
powerful in terms of computing power and memory as cloud. Hence, Edge and Cloud 
computing can be used in combination thereby distributing the huge data volumes across each 
other.  
 
• During normal driving, on boarded cars can collect only a limited amount of data at low 
frequency for forwarding to the cloud. 
• When a problem occurs, or when so instructed by the cloud, on boarded cars can collect the 
data at high frequency for forwarding to the cloud. 
 
Edge computing helps to limit the amount of data that is pushed out, which in turn reduces the 
data transmission costs for end users and also enables near real-time evaluation of data. 
 
Need for edge computing is defined based on the following perspectives: 
 
1) Low Latency data 
Features like Harsh braking (Driving behavior) requires monitoring even less than the 
sampling frequency window and immediate evaluation is also crucial. Therefore, it can 
be detected at edge and a corresponding event can be reported to the cloud. 
2) High throughput data 
 For the default communication frequency, there would be 480 samples per 
communication window. So, an averaging operation can be performed and a single 
consolidated value for each signal can be sent in the communication frequency window 
thereby reducing the overhead in size.
